# Godot project rules (read before changing anything in godot/, and when adding players, clips, cards or packs)

The user also writes Godot code and edits scenes in the editor, so everything must stay editor-friendly: `@export` for settings, `class_name` for
reusable scripts, scenes you can open and see something in. Godot is not installed in the container: nothing here has been run by Claude.
After a change, say what to test and ask the user to paste the Output panel if something fails. Godot version in use: 4.7 (project targets 4.2+).

## Layout (no loose files in a root)
- `scripts/<feature>/` and `scenes/<feature>/` mirror each other: `core`, `packs`, `cards`, `players` (+ `players/states`), `debug`. A new feature gets its own folder in both.
- `shaders/` tracked. `animations/<feature>/` (one subfolder per animated feature: `players/` now; add `packs/`, `ui/`... as they get generated libraries) tracked, GENERATED ones are marked below. `assets/pitches/<stadium_id>/` generated by the `stadiums` export step from data/stadiums.csv, tracked. `scenes/stadium/stadium.tscn` (a 3D scene, Camera3D TV view; players stay 2D and are projected with add_actor) + `scripts/stadium/`; test with scenes/debug/stadium_viewer.tscn.
- Everything animated has a feature folder in `scripts/`, `scenes/` (and `animations/` when generated): players, cards, packs, ...
- `assets/*` (except pitches) and `data/` are generated by the manager tool's Export to game button (`tool/export_game.py`) and git-ignored. Never edit them by hand.

## Data
- `Data` is a static class (`scripts/core/data.gd`, no autoload, so @tool scripts and editor previews work): `Data.table`, `Data.row`, `Data.tex`, `Data.rules`, `Data.anims`.
- CSV columns are a contract with the tool: add columns, never rename or reorder. All values are Strings; convert with `Data.num` / `Data.inum`.
- Anything tweakable (stats, odds, speeds, flows) belongs in a CSV in the repo `data/`, not in a script constant. Script constants marked "placeholder" are to move into data.

## Players and animation
- `scenes/players/player.tscn`: Sprite (passive picture), AnimationPlayer (one Animation per sprite sheet), AnimationTree (flow graph with arrows between clips), StateMachine (gameplay states).
- `PlayerSprite` never animates itself. The AnimationPlayer sets its `sheet` and `frame_index`; `direction` is set by code (`Player.face_vector`).
- Animations are generated: add a clip by baking its sheet (tool: Animations tab / Base animations tab), then press Export. It appears in the Animation panel and in the flow graph.
- Arrows between clips come from `data/animation_flow.csv` (from, to, mode=auto; one outgoing arrow per clip). The export regenerates `animations/players/player_library.tres` and
  `animations/players/player_flow.tres` every time, so edit the CSV (tool: Other tables), NOT the graph in Godot. Commit the regenerated files.
- Gameplay states are child nodes of `StateMachine` (name = state name). Base node `PlayerState` has `clip`, `event_transitions`, `go_to_when_clip_ends`; scripts only override `_on_*` functions.
  New state = new node, or a script extending `PlayerState` with a `class_name` and `@export`ed settings. Do not hard-wire state names in other scripts beyond the ones in the scene.
- States ask for clips with `player.play_clip(name)`; do not touch AnimationPlayer or the sprite from states. Orders to players are events: `player.move_to`, `player.play_action`, `player.send_event`.
- Adding a PLAYER = a row in `data/players.csv` (look columns) + Export (writes `assets/looks/<id>.png` and `assets/faces/<id>.png`). No scene or script change.

- `scenes/debug/animation_viewer.tscn` is the animation viewer (pick player + clip, rotate while playing). Keep it working when the player scene changes.

## Cards
- Player cards are modular: shared layers per rarity / foil style, one face image per player, text and stats drawn live from the row (`PlayerCard`, `PixelText`, `data/card_rules.json`). Never bake stats into images.
- Skill cards are one exported image each (unique emblem art) plus tooltips; adding a card = a row in `cards.csv` + a recipe in `cards/recipes.py` + Export.

## Animation rule for everything (cards, UI, effects, scenes)
- Anything that moves or changes over time is a Godot animation: an AnimationPlayer in the same scene, tracks on exported properties, so it shows in the Animation panel and the user can edit it. No timers, tweens or `_process` counters for authored motion (code may only call `play(name)`).
- Hand-authored (cards: `scenes/cards/*.tscn`: appear, hover_in/out, foil_shimmer, ready, unavailable, use, cooldown_end; packs: `scenes/packs/pack_wrapper.tscn`: appear, hover_in/out, tremble, open) = edit in the editor, not regenerated.
- Generated from data (player clips, flow graph) = regenerated by the export; edit the source table.
- Animate your own `@export` properties (for example `fx_scale`, `foil_frame`) rather than node transforms the caller may set.
- Python-rendered GIFs and previews (`packs/opening.py`, titan scenes, aura effects) are tool previews only. They still have to be ported to Godot scenes with AnimationPlayers / particles / shaders: the pack opening dust/punch, the card reveal sequence, Titan scenes and effects are NOT ported yet (pack_wrapper's `open` is a placeholder).

## Input
- Keys and mouse are Input Map actions in `project.godot`. Scripts use action names only (`is_action_pressed("play_kick")`). New control = new action, never a hard-coded key.

## Editor previews
- Scripts with previews are `@tool`. In @tool code never use autoloads, guard editor-only work with `Engine.is_editor_hint()`, and keep previews harmless in game.

## GDScript pitfalls already hit here
- Do not declare members that Node/Sprite2D already have (`frame`, `name`, `offset`...). Do not call static functions on instances. Avoid parameter names that shadow Node members.
- `Data.tex` falls back to reading the PNG when Godot's import is invalid; keep using it instead of `load()` for exported art.

## When you change something here
Update `godot/README.md`, `docs/DECISIONS.md`, `data/progress.csv`, the Claude Docs design document (14a/14b), and this file if a rule changes. Run `python tool/selftest.py` and the export.

## Stadium and goals (3D)
Placing in the editor: instance scenes/players/player.tscn or scenes/ball/ball.tscn under the stadium's Actors node and set Pitch Position (Preview Player / Ball Id pick the look); Stadium._adopt_placed() registers them at run time. Do not attach scripts by hand (data.gd, ball_physics.gd, goal_net.gd are RefCounted, not nodes).
- `scenes/stadium/stadium.tscn` is a Node3D (Camera3D TV view). Art in `assets/pitches/<id>/` is generated + tracked. Players stay 2D and are projected with `Stadium.add_actor(node, pitch_pos)`.
- Goals: `scripts/stadium/goal.gd` (Goal) + `goal_net.gd` (GoalNet, pure sim). Styles come from `data/goals.csv`. goal_net.gd mirrors `stadiums/goallib.py`: change one, change the other, then re-tune in the tool's Goal simulator tab.
- Stadium look and camera come from `data/stadiums.csv` (Stadiums tab in the tool). Test scene: `scenes/debug/stadium_viewer.tscn` (A/D camera, 1-3 stadium, B shoots).

## Match
- `scenes/match/match.tscn` is the main scene: Match node (MatchGame, `Settings` = `scenes/match/match_settings.tres`), a SubViewport with the Stadium (top 420 px), the Hud CanvasLayer (strip under the pitch, no pop-ups) and Controls. MatchGame is thin: it owns teams, ball, clock and calls the modules in `scripts/match/`: `match_settings.gd` (MatchSettings resource: EVERY tweakable number, grouped, edit in the inspector, save presets as .tres), `match_possession.gd` (carry, pick-up, tackles, kicks through the ball states), `match_motion.gd` (running, animation), `match_rules.gd` (kick-off, goals, throw-ins, corners), `match_orders.gd` (human orders), `match_cards.gd` (the hand), `match_controls.gd` (mouse / pad), `match_hud.gd` + `scenes/match/match_hud.tscn` (the HUD is a real scene you edit in the editor: move / restyle ScorePanel, Who, Orders, HandPanel, TeamPanel, CommandPanel, Message freely, keep the unique-name nodes (%Score, %Hand, ...) and the `Order_<id>` button names; the script only fills them in; `hud_overlay.gd` draws the rings and aim lines; exports `Card Scale`, `Tooltip Scale`, `Team Button Size`; `set_team_commands([{id, label}])` fills the TEAM area, signal `team_command`), `team.gd`, `footballer.gd`. Put a new number in MatchSettings (groups: Possession, Build-up, Team shape, AI, Orders, Order timing, Card effects, Goalkeeper and control), a new behaviour in its own module. Nothing tweakable stays hard-coded: every module's numbers are exports.
- AI is in `scripts/ai/`: `ai_brain.gd` (team phase BUILD_UP / PROGRESS / FINAL_THIRD / ORGANISE / PRESS / TRANSITION, picks the presser, applies intents), `ai_context.gd` (what a team sees: ball, carrier, formation numbers from formations.csv / families, helpers), `ai_intent.gd` (what a player wants), `ai_role.gd` (base: five cases `_with_ball`, `_support`, `_defend`, `_loose`, `_receive`, plus `home_spot()` = slot + styles.csv offset for the phase + team line + slide to the ball) and one file per role in `scripts/ai/roles/` (ai_gk, ai_cb, ai_fullback, ai_cdm, ai_cm, ai_cam, ai_winger, ai_st). Where to stand is named in the pitch map (`scripts/ai/pitch_map.gd`, PitchMap, static; data in `data/pitch_zones.csv` and `data/pitch_spots.csv`, team-frame percentages, edit in the tool's Other tables): in a role use `c.spot("left_half_space_high")`, `c.zone("opp_box")`, `c.in_zone(f.pos, "final_third")`, `c.zones_at(pos)`. It is not a base class: AiContext hands it to every role. Roles react to the formation with `match c.family:` / `match c.formation_id:` / `f.style`. To change how a role plays, edit its file only. Roles are RESOURCES: every role number is an `@export` (groups: Team shape, Pressing and marking, Carrying, Passing, Shooting + a group per role), collected in an AiProfile (`scenes/ai/profile_default.tres`, assigned to MatchSettings > AI > Home Ai / Away Ai). Tune in the inspector; duplicate the .tres for presets and give the teams different ones. New role number = new `@export` on that role, never a literal in a function. Formation-specific play lives in `scripts/ai/formations/` (AiFormation base; `ai_442.gd` = F01: mid block banks, press triggers, overlap/underlap, one CM holds, striker pair), listed in AiProfile > Formations with the formation ids it covers; AiRole.think asks the formation first and falls back to the role when it returns null. One file per formation. F02-F10 (4-3-3, 4-2-3-1, 4-1-4-1, 4-3-2-1, 4-1-2-1-2 diamond, 3-5-2, 3-4-3, 5-3-2, 5-4-1) share `ai_shaped_formation.gd` (AiShapedFormation: lines that trail the ball, press triggers, build-up, one-goes-one-stays, 10 between the lines) and each file is an empty class (`ai_433.gd`, `ai_4231.gd`, ...) and its numbers live on its resource in the profile .tres, never in code, taken from tactico.pro/formations/<name>; all are exports in the profile's Formations list.
- Teams are set in MatchSettings > Match: formation (drop-down of names from formations.csv) and the kit colours (`KitColors` resources: Home Kit / Away Kit / Keeper Kit; change colours in the inspector or use Load Preset to copy a row of kits.csv). Look atlases are exported ONCE per player in fixed KEY colours (`tool/looks.py` KEY_KIT, must match `KitColors.key_map()`); `PlayerSprite` swaps the key colours for the team's colours when the player loads (CPU, 96x24 pixels, cached per player + colours; `KitColors.key_map()`), so there are no per-kit images. `shaders/uv_skin.gdshader` is unchanged (a first shader-side swap did not work on the user's machine). Kit patterns (hoops, stripes) are not in-game; shirts are plain.
- Players are driven in metres (Footballer.pos), not by the Player state machine: MatchMotion calls `stadium.set_actor_pos`, `face_vector` and `play_clip`. The ball is held at the carrier's feet (`ball.hold()`) and released with `Ball.play_action("pass" / "through" / "lob" / "shot", ...)`.
- Controls (`match_controls.gd`): mouse or controller, never a keyboard walk. Double click a team mate = the carrier passes; right click (Square) = lob there; right-button DRAG (Square held) from the carrier = lob with snapping (to a mate; further = over the top, he runs; a spot / the goal area = a cross); left drag from the carrier = pass / through / shoot (see Current command; time slows to `Aim Slowmo`); drag from any other player = a run; click a player = the order buttons in the HUD strip light up (Through / Run with the ball; Run / Press / Tackle without); Esc / Circle cancels. The controller moves the real mouse pointer (stick) and sends left-button events (Cross = click, Triangle held = drag). Actions: ptr_left/right/up/down, ptr_click, ptr_grab, ptr_lob, ptr_cancel, m_restart.
- Camera: the stadium's own TV camera (data/stadiums.csv) cuts off the near touchline, so the match uses its own (MatchSettings > Camera: height, back, look Z, fov, follow speed; tick Use Stadium Camera for the old one). Pixel size of players follows from it.
- The HUD has no help text any more: the right-hand box is the current command. Controls are documented here and in MatchControls' header.
- Layout: the pitch is a SubViewport (top 420 px of the 960x540 screen) and the HUD is the strip under it, so nothing covers the play; pointer and screen coordinates are the same in both because the view starts at (0, 0).

## HUD art and pixel UI (decided: 1:1 pixels, card language, generated)
- The HUD is pixel art in the language of the cards: dark field (12,13,20), 1 px frame with cut corners, the 3x5 pixel font, category colours. Everything at 1:1 on the 960x540 screen (the same pixel size as the sprites and the cards at their real 64x90): never scale pixel art by a non-whole number (cards in the hand are scale 1, the tooltip 2).
- Art is GENERATED by `hud/hudlib.py` (colours in `data/hud_style.csv`, edit in the tool's Other tables) into `assets/ui/` by the export step "HUD art" (panel, button_normal / hover / pressed / disabled / active, strip, ring_select, ring_target). Preview without the tool: `python hud/hudlib.py out.png` (a mock of the whole match screen with real cards). New HUD art = a function in hudlib.py, never a hand-painted PNG. The near-white frames are tinted in the game by an `accent` colour (team kit, command kind).
- Godot nodes in `scripts/ui/` (use them for ALL HUD / menu UI, not Label / Button / Panel): `PixelPanel` (nine-patch frame, `accent`), `PixelLabel` (pixel font, `text_scale` whole numbers, `align`, `wrap`, `shadow`), `PixelButton` (Button-like: `text`, `disabled`, `toggle_mode`, `button_pressed`, signals `pressed` / `toggled`), `PixelImage` (draws an exported image 1:1), `PixelUi` (nine-patch helper). They are @tool and draw blank until the HUD art has been exported.
- Strip layout (960x540): left column x 4-196 (score panel, selected player, 2x2 order buttons), hand panel x 200-739 (8 cards of 64x90, 3 px apart), right column x 742-956 (TEAM stance buttons, then the current command panel). Keep these free of overlap when you move things.

## Team control: stances (dev rules)
- Every team plays INSIDE its formation. The formation (data/formations.csv numbers + its file in `scripts/ai/formations/`, e.g. `ai_442.gd`) is the team's brain: it organises the banks, decides when to press, parks the block, who overlaps. Nothing else moves the team around.
- A STANCE (`scripts/ai/team_stance.gd`, TeamStance resource, list in AiProfile > Stances, edited in `scenes/ai/profile_default.tres`) leans the formation: it ADDS deltas to its 8 numbers (line height, width, compactness, press, overlap, directness, counter, risk) and sets `block_shift` (metres the block moves up/down), `push_scale`, `press_always` (press whenever in reach) and `press_never` (park the bus: contain, never chase). Stances: auto (formation as designed), press_high, mid_block, park_bus, push_up, counter. Add one = a new TeamStance in the profile (it appears as a TEAM button by itself).
- `Team.stance_id` is the stance in force ("auto" by default for both sides). The HUD TEAM buttons set the home side's (`MatchGame._on_team_command`). For "auto" the profile's rules pick one by minute and score (AiProfile > Stances: park a lead after minute 80, press when behind after 60). `AiBrain._stance(c)` resolves it every frame; `AiContext.set_stance` produces `c.form` (formation numbers + deltas) and `c.stance`; roles and formation files read `c.f("press")`, `c.stance.block_shift` etc.
- Rule for formation files: read the stance (block_shift in the block depth, press_always / press_never in the press decision) and fall back to the role AI (return null) for everything else, so every new formation file gets stances for free. Roles read `c.stance.push_scale` in `home_spot()` and `press_never` in `_defend()`.

## Current command (HUD state store)
- `MatchCommand` (`scripts/match/match_command.gd`, owned by MatchGame as `command`) is the one thing the human is doing now: `kind` (pass, through, lob, shoot, run, press, tackle, card, team), `text`, `note`, `who`, `target`. `command.show(kind, text, who, target, note, hold)`: hold 0 = live (the drag in progress, stays until replaced or cleared), hold > 0 = an order just given (clears itself after `MatchSettings.command_hold`). `signal changed`.
- Writers: MatchControls (live while dragging), MatchOrders (every order given), MatchCards (a card played), MatchGame (a team stance chosen). Reader: MatchHud (`bind_command`): the box under the order buttons shows the text in the kind's colour (`MatchHud.KIND_COLORS`) and the note, and rings `command.target` on the pitch (a through ball marks him RUN). Any new action just calls `command.show(...)`; do not add HUD code per action.
- Drag from the ball carrier (MatchControls exports `Snap Radius`, `Through Pull`, `Shoot Zone X/Z`): snaps to the nearest team mate = PASS; dragged further than Through Pull = THROUGH (the mate runs onto it); pointer in the goal area = SHOOT; elsewhere = pass to space.

## Ball
- Ball states (`scripts/ball/states/`, nodes under Ball > StateMachine in scenes/ball/ball.tscn): Free, Held and the kick states Pass, Through, Lob, Shot (`BallKick`, `action_id` = a row of `data/ball_actions.csv`: kick style, speed rule, lead, accuracy stat). `Ball.play_action(action, target, kicker_row, target_vel, over)` plans the kick in the state, kicks and enters it; a flight state returns to Free when the ball stops. `Ball.state_changed(from, to)` is for AI / HUD to react. Add a state = add a node (and a row in ball_actions.csv for kicks).
- `scripts/ball/ball_physics.gd` (BallPhysics, pure sim) mirrors `balls/balllib.py`: change one, change the other, tune in the tool's Ball studio tab. Numbers come from `data/balls.csv` (gravity, air drag, swerve, knuckle wobble, dip, bounce, grip, rolling, spin decay, mass, radius) plus gameplay factors `touch` (first touch / control) and `power` (kick speed). Panel maps (`assets/balls/<id>_map.png`, wrapped round the ball by `shaders/ball.gdshader` using the ball's real spin) are generated by the `balls` export step. Kick styles (`data/kick_styles.csv`) give each kick its spin: `Ball.kick(from, aim, style_id, strength)`.
- `Ball` (scripts/ball, scenes/ball/ball.tscn; its Sprite and Shadow are created in code so the scene stays clean; the AnimationPlayer library `animations/ball/ball_library.tres` is GENERATED every export: idle + one clip per kick style, which set `preview_spin` so you can watch each kick spin in the Animation tab): `Ball.create(id)`, `stadium.add_ball(b)`, `b.launch(from, dir, speed, spin, seed)`. Use `b.power()` when computing kicks and `b.touch()` for control rolls. Pixel sprite is only display; collisions are 3D (players = footprint circle on the ground + height, goals via Stadium.ball_update).


## HUD layout is editable in the scene (match_hud.tscn)
Every HUD group is a panel with its parts inside it: OrdersPanel (Who, Orders), HandPanel (Hand = HandBar: Slot1..Slot8, each a SkillCard you can see in the tree; the game fills the used ones and hides the rest), TeamPanel (TeamTitle, TeamGrid with the Stance_ buttons, TeamNote), CommandPanel (CommandTitle, CommandNote), plus Scorebug, Message, Strip and Overlay.
Move / resize any of them in the 2D view; panels anchor to the screen edges (left / centre / right of the bottom strip). The hand is not laid out by code: move the Slot nodes and set each Card's Scale in the scene (HandBar only lists the cards). The stance buttons are real nodes in TeamGrid named Stance_<id> (auto, press_high, mid_block, park_bus, push_up, counter): move / restyle them freely; the game binds them by name, shows only the stances the AI profile has and fills the tooltip. A new stance in the profile needs a new Stance_<id> button.
Nothing links the Strip height to the pitch view in code: when you change the strip, set the bottom offset of View (match.tscn) and of Overlay (match_hud.tscn) to minus the strip height. Re-run Export to game after changing hudlib's strip size (strip art is tiled).

## AI interaction layer (team play, not every player for himself)
`scripts/ai/ai_interact.gd` (AiInteract, AiProfile > Interact, all exports) runs AFTER the role / formation decided each player: `compute(c)` once per team per frame, `post(f, intent, c)` per player.
- Cover: a back-line player who steps out (the presser, or `step_gap` m ahead of the line) or a CDM / CM who presses gets a cover: the nearest team mate falls in behind him (`c.cover[f]`), the rest of the back line slides towards the push (`compress`).
- Outlet: when one of our midfielders (or any `outlet_presser_roles`) is the presser, the striker (`outlet_roles`) goes looking for free space ahead on the far side (`_space()`: far from opponents, never offside, retargets every `outlet_retarget` s).
- Traits (`AiTrait`, ids in `players.csv` column `traits`, separated by space or |): "roamer" = the Messi type (Zionel Pessi PL055): never presses (`exempt_press`), walks (`walk_factor`) in space `counter_ahead` m ahead of the ball while the team defends, roams into free space in attack, sprints for `sprint_after_win` s after a turnover. New trait = exports on AiTrait + a branch in `AiInteract._trait`.
- Context additions (AiContext): `cover`, `pushers`, `push_y`, `outlet`, `poss_time`. Footballer.ai = per-player AI memory. New team-level behaviour goes in AiInteract, not in each role.

## AI resources are separate files (no nested sub-menus)
`scenes/ai/profile_default.tres` only LINKS to files: `scenes/ai/roles/*.tres` (one per role), `formations/f01_442.tres, f02.tres ... f10.tres` (the numbers of each formation), `stances/*.tres`, `interact.tres`, `traits/*.tres`. Open the file you want to tune from the FileSystem dock (or click a link in the profile and use the inspector's "Edit" / open-in-new-tab) instead of digging through sub-resources. A new formation / stance / trait = a new .tres next to the others and one more entry in the profile's list.

## Adding a formation from the inspector
MatchSettings > Match > Custom Formations: add an element, New FormationLayout (`scripts/ai/formation_layout.gd`): id, layout_name, family, the ten outfield slots (FormationSlot: role, style, x across 0-100, y along 0-100 = the columns of data/formation_slots.csv), optional shape numbers (-1 = family default) and optional `play` (an AiShapedFormation: press / block numbers; empty = the shared defaults). It then shows in the Home / Away Formation lists. Save it as a .tres in `scenes/ai/layouts/` (see `example_3421.tres`, a 3-4-2-1). Lookup is `MatchSettings.layout(name_or_id)`, used by `Team.build`, `AiContext.setup` and `AiProfile.formation_for`. The 10 built-in formations still come from data/formations.csv (the manager tool); custom ones are Godot-only for now.

## Ball touch and keeper saves
- Ball drawn at `MatchSettings.ball_scale` (Ball.visual_scale). First touch: the ball eases to the foot over `settle_time` at `settle_rate`, and `control_cushion` kills part of his speed (no snap).
- `scripts/match/match_keeper.gd` (MatchKeeper): on-target shots make the keeper play a clip picked at random from the lists in MatchSettings > Goalkeeper saves (catch / claim / palm / low / mid / far; add clip names to add variants). He moves to the ball line, and at the clip's `strike` key the save resolves: catch, deflect or miss. Left dives play the clip mirrored (`Footballer.mirror` -> `Player.set_mirror`). Untested in Godot.

## Camera
`scripts/camera/camera_rig.gd` (CameraRig) is the script on the Camera node in scenes/stadium/stadium.tscn; all camera numbers are its inspector exports (Orbit: yaw / pitch / distance / fov / aim offset; Follow: speed, limit, pan; Stadium: use_stadium_layout). Rotating around the players = yaw_deg, or `orbit_to(yaw, pitch, dist, seconds)` from code. MatchSettings no longer has camera settings. Untested in Godot.

## Kicks turn first, and can stumble
`scripts/match/match_kicking.gd` (MatchKicking, `g.kicking`): `MatchPossession.kick_action` hands every kick to it. If the target is more than `pivot_min_deg` away from where he faces, he pivots (ball stays at his feet, `Footballer.aim` / `aim_done`) and then plays the kick clip. At the strike frame a pass can be scuffed (more aim error; chance from PAS, nearest opponent, kicking before the turn is done) and he stumbles / falls after it (clips in MatchSettings > Kick turn and stumble). AI and human kicks both use it; card kicks (match_cards) still kick instantly. Untested in Godot.

## AI behaviours (add a decision without touching the roles)
`scripts/ai/behaviours/ai_behaviour.gd` (AiBehaviour, a Resource). Add one = copy `ai_jockey.gd` in that folder, rename file + `class_name`, set `roles` / `when` in `_init()`, override `wants(f, c, role) -> bool` (when) and `act(f, c, role, dt) -> AiIntent` (what). Nothing else: `AiBehaviour.discover()` scans the folder at run time and `AiProfile.all_behaviours()` hands every script to every profile (no .tres, no list). `AiRole.think` tries them after the formation file and before the role's five cases, lowest `priority` first then file name; the first `wants()` yes wins. Exports: `enabled`, `priority`, `roles` (empty = all), `when` (Receiving / With ball / Support / Loose / Defending flags). Optional override with numbers set in the inspector: a resource at `scenes/ai/behaviours/<file name minus "ai_" and ".gd">.tres` (`jockey.tres`, used instead of the script defaults; it has `enabled = false`, tick it to try the jockey). AiProfile > Behaviours = per-team copies (replace the automatic one of the same script) or extras. Untested in Godot.

## Playtest fixes (keeper, touch, facing)
- Godot 4.5 can be run headless in the cloud container (download from GitHub releases into a scratch folder; `--headless --fixed-fps 60 --path godot --script x.gd`, run `tool/export_game.py data` first and delete `godot/data/progress.csv`). Matches simulate at ~6x real time; use it to measure balance instead of guessing.
- Keeper (`match_keeper.gd`): only opponents' shots start a dive; the save is resolved the moment the ball is in reach inside a window around the clip's strike frame (`save_window_before/after`, the ball is slower than the straight-line guess); then a skill roll (REF + HAN, sideways distance) decides stop / parry / beat. ## Aerial contests (lobs)
- `scripts/aerial/match_aerial.gd` (MatchAerial, `g.aerial`, MatchSettings > Aerial duels) + `landing_marker.gd` (the yellow ring on the grass, an actor of the stadium that shrinks as the ball comes down). - `scripts/ai/behaviours/ai_contest.gd` (priority -10): those two go to the spot (sprint, then jog) and WAIT there facing the ball (`f.ai["air_wait"]` makes MatchMotion play `ct01_wait_air`); nobody drifts back to his slot. Alone under it he just takes it with the normal pick-up.
- Both there when the ball is `aerial_trigger` s from head height: each makes a plan (`_plan`): approach = shove-and-chest (PHY >= push_phy and push_margin more than him: `ct02_push_chest`, the loser stumbles / falls, the winner takes it at his feet), shoulder leap (PAS+DRI average >= smart_min and him within leap_range: `ct03_shoulder_leap`, bonus) or plain header; score = heading (PHY with DEF for defensive roles, SHO for the rest) + jump_share x PHY + noise + bonus. The winner's clip is stretched so its strike frame meets the ball; at the strike frame (ball within header_reach and header height) he clears (defensive roles; `df16_header_clear`), shoots (inside head_shoot_range; `sh12_power_header`) or heads to the best free team mate (`sh11_glancing_header`) through `Ball.play_action` with the speeds in settings. The loser plays `base_jump`.
