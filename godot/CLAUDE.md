# Godot project rules (read before changing anything in godot/, and when adding players, clips, cards or packs)

The user also writes Godot code and edits scenes in the editor, so everything must stay editor-friendly: `@export` for settings, `class_name` for
reusable scripts, scenes you can open and see something in. Godot is not installed in the container: nothing here has been run by Claude.
After a change, say what to test and ask the user to paste the Output panel if something fails. Godot version in use: 4.7 (project targets 4.2+).

## Layout (no loose files in a root)
- `scripts/<feature>/` and `scenes/<feature>/` mirror each other: `core`, `packs`, `cards`, `players` (+ `players/states`), `debug`. A new feature gets its own folder in both.
- `shaders/` tracked. `animations/<feature>/` (one subfolder per animated feature: `players/` now; add `packs/`, `ui/`... as they get generated libraries) tracked, GENERATED ones are marked below. `assets/pitches/<stadium_id>/` generated by the `stadiums` export step from data/stadiums.csv, tracked. `scenes/stadium/stadium.tscn` (a 3D scene, Camera3D TV view; players stay 2D and are projected with add_actor) + `scripts/stadium/`; test with scenes/debug/stadium_viewer.tscn.
- Everything animated has a feature folder in `scripts/`, `scenes/` (and `animations/` when generated): players, cards, packs, ...
- `assets/*` (except pitches) and `data/` are generated by the manager tool's Export to game button (`tool/export_game.py`) and git-ignored. Never edit them by hand.

## Data
- `Data` is a static class (`scripts/core/data.gd`, no autoload, so @tool scripts and editor previews work): `Data.table`, `Data.row`, `Data.tex`, `Data.rules`, `Data.anims`.
- CSV columns are a contract with the tool: add columns, never rename or reorder. All values are Strings; convert with `Data.num` / `Data.inum`.
- Anything tweakable (stats, odds, speeds, flows) belongs in a CSV in the repo `data/`, not in a script constant. Script constants marked "placeholder" are to move into data.

## Players and animation
- `scenes/players/player.tscn`: Sprite (passive picture), AnimationPlayer (one Animation per sprite sheet), AnimationTree (flow graph with arrows between clips), StateMachine (gameplay states).
- `PlayerSprite` never animates itself. The AnimationPlayer sets its `sheet` and `frame_index`; `direction` is set by code (`Player.face_vector`).
- Animations are generated: add a clip by baking its sheet (tool: Animations tab / Base animations tab), then press Export. It appears in the Animation panel and in the flow graph.
- Arrows between clips come from `data/animation_flow.csv` (from, to, mode=auto; one outgoing arrow per clip). The export regenerates `animations/players/player_library.tres` and
  `animations/players/player_flow.tres` every time, so edit the CSV (tool: Other tables), NOT the graph in Godot. Commit the regenerated files.
- Gameplay states are child nodes of `StateMachine` (name = state name). Base node `PlayerState` has `clip`, `event_transitions`, `go_to_when_clip_ends`; scripts only override `_on_*` functions.
  New state = new node, or a script extending `PlayerState` with a `class_name` and `@export`ed settings. Do not hard-wire state names in other scripts beyond the ones in the scene.
- States ask for clips with `player.play_clip(name)`; do not touch AnimationPlayer or the sprite from states. Orders to players are events: `player.move_to`, `player.play_action`, `player.send_event`.
- Adding a PLAYER = a row in `data/players.csv` (look columns) + Export (writes `assets/looks/<id>.png` and `assets/faces/<id>.png`). No scene or script change.

- `scenes/debug/animation_viewer.tscn` is the animation viewer (pick player + clip, rotate while playing). Keep it working when the player scene changes.

## Cards
- Player cards are modular: shared layers per rarity / foil style, one face image per player, text and stats drawn live from the row (`PlayerCard`, `PixelText`, `data/card_rules.json`). Never bake stats into images.
- Skill cards are one exported image each (unique emblem art) plus tooltips; adding a card = a row in `cards.csv` + a recipe in `cards/recipes.py` + Export.

## Animation rule for everything (cards, UI, effects, scenes)
- Anything that moves or changes over time is a Godot animation: an AnimationPlayer in the same scene, tracks on exported properties, so it shows in the Animation panel and the user can edit it. No timers, tweens or `_process` counters for authored motion (code may only call `play(name)`).
- Hand-authored (cards: `scenes/cards/*.tscn`: appear, hover_in/out, foil_shimmer, ready, unavailable, use, cooldown_end; packs: `scenes/packs/pack_wrapper.tscn`: appear, hover_in/out, tremble, open) = edit in the editor, not regenerated.
- Generated from data (player clips, flow graph) = regenerated by the export; edit the source table.
- Animate your own `@export` properties (for example `fx_scale`, `foil_frame`) rather than node transforms the caller may set.
- Python-rendered GIFs and previews (`packs/opening.py`, titan scenes, aura effects) are tool previews only. They still have to be ported to Godot scenes with AnimationPlayers / particles / shaders: the pack opening dust/punch, the card reveal sequence, Titan scenes and effects are NOT ported yet (pack_wrapper's `open` is a placeholder).

## Input
- Keys and mouse are Input Map actions in `project.godot`. Scripts use action names only (`is_action_pressed("play_kick")`). New control = new action, never a hard-coded key.

## Editor previews
- Scripts with previews are `@tool`. In @tool code never use autoloads, guard editor-only work with `Engine.is_editor_hint()`, and keep previews harmless in game.

## GDScript pitfalls already hit here
- Do not declare members that Node/Sprite2D already have (`frame`, `name`, `offset`...). Do not call static functions on instances. Avoid parameter names that shadow Node members.
- `Data.tex` falls back to reading the PNG when Godot's import is invalid; keep using it instead of `load()` for exported art.

## When you change something here
Update `godot/README.md`, `docs/DECISIONS.md`, `data/progress.csv`, the Claude Docs design document (14a/14b), and this file if a rule changes. Run `python tool/selftest.py` and the export.

## Stadium and goals (3D)
Placing in the editor: instance scenes/players/player.tscn or scenes/ball/ball.tscn under the stadium's Actors node and set Pitch Position (Preview Player / Ball Id pick the look); Stadium._adopt_placed() registers them at run time. Do not attach scripts by hand (data.gd, ball_physics.gd, goal_net.gd are RefCounted, not nodes).
- `scenes/stadium/stadium.tscn` is a Node3D (Camera3D TV view). Art in `assets/pitches/<id>/` is generated + tracked. Players stay 2D and are projected with `Stadium.add_actor(node, pitch_pos)`.
- Goals: `scripts/stadium/goal.gd` (Goal) + `goal_net.gd` (GoalNet, pure sim). Styles come from `data/goals.csv`. goal_net.gd mirrors `stadiums/goallib.py`: change one, change the other, then re-tune in the tool's Goal simulator tab.
- Stadium look and camera come from `data/stadiums.csv` (Stadiums tab in the tool). Test scene: `scenes/debug/stadium_viewer.tscn` (A/D camera, 1-3 stadium, B shoots).

## Match
- `scenes/match/match.tscn` is the main scene: Match node (MatchGame, `Settings` = `scenes/match/match_settings.tres`), a SubViewport with the Stadium (top 420 px), the Hud CanvasLayer (strip under the pitch, no pop-ups) and Controls. MatchGame is thin: it owns teams, ball, clock and calls the modules in `scripts/match/`: `match_settings.gd` (MatchSettings resource: EVERY tweakable number, grouped, edit in the inspector, save presets as .tres), `match_possession.gd` (carry, pick-up, tackles, kicks through the ball states), `match_motion.gd` (running, animation), `match_rules.gd` (kick-off, goals, throw-ins, corners), `match_orders.gd` (human orders), `match_cards.gd` (the hand), `match_controls.gd` (mouse / pad), `match_hud.gd` (exports `Card Scale`, `Tooltip Scale`; `set_team_commands([{id, label}])` fills the TEAM area, signal `team_command`), `team.gd`, `footballer.gd`. Put a new number in MatchSettings (groups: Possession, Build-up, Team shape, AI, Orders, Order timing, Card effects, Goalkeeper and control), a new behaviour in its own module. Nothing tweakable stays hard-coded: every module's numbers are exports.
- AI is in `scripts/ai/`: `ai_brain.gd` (team phase BUILD_UP / PROGRESS / FINAL_THIRD / ORGANISE / PRESS / TRANSITION, picks the presser, applies intents), `ai_context.gd` (what a team sees: ball, carrier, formation numbers from formations.csv / families, helpers), `ai_intent.gd` (what a player wants), `ai_role.gd` (base: five cases `_with_ball`, `_support`, `_defend`, `_loose`, `_receive`, plus `home_spot()` = slot + styles.csv offset for the phase + team line + slide to the ball) and one file per role in `scripts/ai/roles/` (ai_gk, ai_cb, ai_fullback, ai_cdm, ai_cm, ai_cam, ai_winger, ai_st). Where to stand is named in the pitch map (`scripts/ai/pitch_map.gd`, PitchMap, static; data in `data/pitch_zones.csv` and `data/pitch_spots.csv`, team-frame percentages, edit in the tool's Other tables): in a role use `c.spot("left_half_space_high")`, `c.zone("opp_box")`, `c.in_zone(f.pos, "final_third")`, `c.zones_at(pos)`. It is not a base class: AiContext hands it to every role. Roles react to the formation with `match c.family:` / `match c.formation_id:` / `f.style`. To change how a role plays, edit its file only. Roles are RESOURCES: every role number is an `@export` (groups: Team shape, Pressing and marking, Carrying, Passing, Shooting + a group per role), collected in an AiProfile (`scenes/ai/profile_default.tres`, assigned to MatchSettings > AI > Home Ai / Away Ai). Tune in the inspector; duplicate the .tres for presets and give the teams different ones. New role number = new `@export` on that role, never a literal in a function. Formation-specific play lives in `scripts/ai/formations/` (AiFormation base; `ai_442.gd` = F01: mid block banks, press triggers, overlap/underlap, one CM holds, striker pair), listed in AiProfile > Formations with the formation ids it covers; AiRole.think asks the formation first and falls back to the role when it returns null. One file per formation.
- Teams are set in MatchSettings > Match: formation (drop-down of names from formations.csv) and the kit colours (`KitColors` resources: Home Kit / Away Kit / Keeper Kit; change colours in the inspector or use Load Preset to copy a row of kits.csv). Look atlases are exported ONCE per player in fixed KEY colours (`tool/looks.py` KEY_KIT, must match `KitColors.key_map()`); `PlayerSprite` swaps the key colours for the team's colours when the player loads (CPU, 96x24 pixels, cached per player + colours; `KitColors.key_map()`), so there are no per-kit images. `shaders/uv_skin.gdshader` is unchanged (a first shader-side swap did not work on the user's machine). Kit patterns (hoops, stripes) are not in-game; shirts are plain.
- Players are driven in metres (Footballer.pos), not by the Player state machine: MatchMotion calls `stadium.set_actor_pos`, `face_vector` and `play_clip`. The ball is held at the carrier's feet (`ball.hold()`) and released with `Ball.play_action("pass" / "through" / "lob" / "shot", ...)`.
- Controls (`match_controls.gd`): mouse or controller, never a keyboard walk. Double click a team mate = the carrier passes; right click (Square) = lob; drag from the ball carrier = shoot (time slows to `Aim Slowmo`); drag from any other player = a run; click a player = the order buttons in the HUD strip light up (Through / Run with the ball; Run / Press / Tackle without); Esc / Circle cancels. The controller moves the real mouse pointer (stick) and sends left-button events (Cross = click, Triangle held = drag). Actions: ptr_left/right/up/down, ptr_click, ptr_grab, ptr_lob, ptr_cancel, m_restart.
- Layout: the pitch is a SubViewport (top 420 px of the 960x540 screen) and the HUD is the strip under it, so nothing covers the play; pointer and screen coordinates are the same in both because the view starts at (0, 0).

## Ball
- Ball states (`scripts/ball/states/`, nodes under Ball > StateMachine in scenes/ball/ball.tscn): Free, Held and the kick states Pass, Through, Lob, Shot (`BallKick`, `action_id` = a row of `data/ball_actions.csv`: kick style, speed rule, lead, accuracy stat). `Ball.play_action(action, target, kicker_row, target_vel, over)` plans the kick in the state, kicks and enters it; a flight state returns to Free when the ball stops. `Ball.state_changed(from, to)` is for AI / HUD to react. Add a state = add a node (and a row in ball_actions.csv for kicks).
- `scripts/ball/ball_physics.gd` (BallPhysics, pure sim) mirrors `balls/balllib.py`: change one, change the other, tune in the tool's Ball studio tab. Numbers come from `data/balls.csv` (gravity, air drag, swerve, knuckle wobble, dip, bounce, grip, rolling, spin decay, mass, radius) plus gameplay factors `touch` (first touch / control) and `power` (kick speed). Panel maps (`assets/balls/<id>_map.png`, wrapped round the ball by `shaders/ball.gdshader` using the ball's real spin) are generated by the `balls` export step. Kick styles (`data/kick_styles.csv`) give each kick its spin: `Ball.kick(from, aim, style_id, strength)`.
- `Ball` (scripts/ball, scenes/ball/ball.tscn; its Sprite and Shadow are created in code so the scene stays clean; the AnimationPlayer library `animations/ball/ball_library.tres` is GENERATED every export: idle + one clip per kick style, which set `preview_spin` so you can watch each kick spin in the Animation tab): `Ball.create(id)`, `stadium.add_ball(b)`, `b.launch(from, dir, speed, spin, seed)`. Use `b.power()` when computing kicks and `b.touch()` for control rolls. Pixel sprite is only display; collisions are 3D (players = footprint circle on the ground + height, goals via Stadium.ball_update).
